# 05 — Opportunity Scoring Engine

> **Master spec:** [`../ARCHITECTURE.md`](../ARCHITECTURE.md) §12 (Opportunity Engine) + §15 (Ranking) · DB: [`01-database-design.md`](./01-database-design.md) §3.13–3.14
> **Status:** Implementation-ready
> **Two jobs, one document:** (A) the **Opportunity Engine** — assemble opportunities from signals+graph and classify Gold/Silver/Bronze; (B) the **Scoring Engine** — compute the multi-score vector that ranks them. They are separate modules that share triggers.

---

## 1. Concepts & Invariants

| # | Invariant | Why |
|---|---|---|
| **O1** | An **Opportunity** is a *derived, mutable projection* over immutable signals+evidence — regenerable at any time. | Enrich-never-replace; replayability (blueprint I4). |
| **O2** | **Tiering is a deterministic gate** on presence-of-fields, then ranked *within* tier by score. | Predictable, explainable classification. |
| **O3** | **Multiple independent scores, each explainable.** Never one opaque number. | "Confident it's Acme" ≠ "Acme is buying"; collapsing hides *why*. |
| **O4** | **Continuous promotion/demotion; every transition recorded.** Never delete to demote. | The promotion ledger is product value. |
| **O5** | **Weights are runtime config**, not code. | Tune without redeploy (FR-SCORE-3). |
| **O6** | **Scores are time-dependent** (decay) even with no new data. | Intent decays; a nightly sweep recomputes. |

## 2. Signals — the raw material

Signals (`signal` table) are classified buying-intent events produced by the `signals` classifiers (blueprint §13/§14) and consumed by the opportunity engine.

### 2.1 Signal taxonomy
| `signal_type` | Meaning | `intent_axis` examples | Typical strength |
|---|---|---|---|
| `funding_raised` | round announced | growth, tooling-budget | 0.7 |
| `hiring` | job posting(s) | role→department axis (sales, revops, email, data) | 0.5–0.7 |
| `tech_adoption` | adopted a tool | that tool's category | 0.6 |
| `tech_churn` | dropped/replacing a tool | competitor-switch | 0.8 |
| `product_launch` | shipped product | scaling | 0.5 |
| `pain_mention` | public complaint/question | crm, deliverability, analytics… | 0.6–0.9 |
| `leadership_change` | new exec | department of exec | 0.6 |
| `expansion` | new market/office | growth | 0.5 |
| `partnership` | integration/partner | ecosystem | 0.4 |

Each signal carries `strength ∈ [0,1]` (raw, from the classifier), `intent_axis`, `evidence_ids[]` (non-empty), and `detected_at`. `decayed_score` is (re)computed by the decay sweep (§6.2).

## 3. Opportunity Templates (motifs)

Opportunities are generated by **declarative templates** — patterns over a company's signal set + graph — so new opportunity types are config, not code (O1).

```yaml
# packages/opportunities/templates/crm_in_market.yaml
id: crm_in_market
thesis: "In-market for CRM"
intent_axis: crm
requires_signals:                 # at least min_signals of these must be present
  - { type: funding_raised, within_days: 180 }
  - { type: hiring, department_in: [sales, revops], within_days: 120 }
  - { type: pain_mention, axis_in: [crm, deliverability], within_days: 90 }
min_signals: 2
suggested_department: Sales
suggested_decision_maker_role: [VP Sales, Head of RevOps, Head of Growth]
base_intent_weight: 0.8
```

```yaml
# deliverability_pain.yaml
id: deliverability_pain
thesis: "Email deliverability pain"
intent_axis: deliverability
requires_signals:
  - { type: pain_mention, axis_in: [deliverability, bounce, spam], within_days: 60 }
  - { type: hiring, department_in: [email, growth, marketing], within_days: 120 }
min_signals: 1                    # a strong pain mention alone qualifies (Bronze)
suggested_department: Marketing
suggested_decision_maker_role: [Head of Growth, Email Marketing Lead, VP Marketing]
base_intent_weight: 0.7
```

**Engine behavior:** for each company touched by a new signal/entity change, evaluate all templates against its current signal set + graph; a match yields or updates an `opportunity` row (unique on `(company_entity_id, template_id)`), sets department/role suggestions (satisfying Silver requirements), and links triggering `evidence`.

## 4. Tiering (the Gold/Silver/Bronze gate)

Deterministic classification over presence-of-fields (O2), exactly per the master spec:

```python
def classify(opp) -> Tier:
    h = opp.presence
    if (h.person and h.company and h.domain and h.role
            and h.relationship_evidence and h.buying_signal):
        return GOLD
    if (h.company and h.domain and h.buying_signal
            and h.suggested_department and h.suggested_role):
        return SILVER
    if h.company and h.domain and h.weak_signal:
        return BRONZE
    return UNQUALIFIED
```

| Tier | Hard requirements |
|---|---|
| **GOLD** | person name · current company · domain · current role · **relationship evidence** (person↔company) · buying signal |
| **SILVER** | company · domain · buying signal · inferred department · inferred decision-maker role (person unknown) |
| **BRONZE** | company · domain · weak/early buying signal |

`relationship_evidence` = at least one `works_at` edge (person→company) backed by evidence (doc 02). This is the precise line between Silver and Gold.

## 5. The Promotion Flywheel (Bronze → Silver → Gold)

On **every** new signal/evidence/entity change touching a company (`opportunity` worker, triggered by `signals.candidate` and `entity.upserted`):

```
1. regenerate candidate opportunities from templates   (O1)
2. re-run tier classify()                              (O2)
3. if tier changed:
      INSERT opportunity_transition(from, to, reason, score_delta)   (O4)
      audit_event('tier_change', ...)
4. recompute score vector (§6)                         (O3, O6)
5. re-index into OpenSearch (doc 06)
```

- **Promotion** examples: Bronze (domain+weak signal) → **Silver** when a qualifying signal + inferable department/role appear → **Gold** the moment a specific person in the right role is resolved *with relationship evidence*.
- **Demotion** (evidence decayed/contradicted) is **also a recorded transition** — never a delete (O4). The operator sees the full arc.
- The `opportunity_transition` ledger powers the "recently upgraded" digest (doc 06/07) and the promotion-rate KPI (blueprint §22).

### 5.1 Decision-maker inference (Silver)
When the person is unknown, infer *who to look for*: `(signal_type + industry + company_size) → (department, role)` via a rules table (from the template's `suggested_*` plus firmographic refinement), e.g. `crm_in_market` + SMB → "Head of Sales / RevOps"; + enterprise → "VP Sales Ops / CRM Admin". Later learned from Gold outcomes (§9).

## 6. Scoring Engine — the multi-score vector

Eight scores (O3), all ∈ [0,1] unless noted, each stored in `score` with a `components jsonb` breakdown (explainability, FR-SCORE-2). Weights `w*`, decay `τ`, and coefficients live in the active `scoring_config` row (O5).

### 6.1 The scores & formulas

**1. Identity Confidence (IC)** — is the *person* one real, correctly-resolved individual?
```
IC = sigmoid( a1·match_prob + a2·log(1+distinct_sources) + a3·handle_verified − a4·conflict_penalty )
```

**2. Company Confidence (CC)** — company resolution certainty + firmographic completeness.
```
CC = sigmoid( b1·domain_verified + b2·log(1+distinct_sources) + b3·firmographic_completeness − b4·alias_conflict )
```

**3. Buying Intent (BI)** — noisy-OR over intent signals; independent signals compound, each decays.
```
BI = 1 − Π_over_signals ( 1 − strength_i · intent_weight(type_i) · freshness_i )
```

**4. Evidence Score (ES)** — quantity × quality × independence, with a source-diversity bonus.
```
ES = tanh( Σ_i source_trust_i · freshness_i ) · (1 + diversity_bonus(distinct_source_domains))
```

**5. Freshness (FR)** — recency of the driving signals; τ per signal type.
```
FR = exp( −(now − most_recent_signal_at) / τ(type) )
     τ_funding ≈ 180d,  τ_hiring ≈ 90d,  τ_pain ≈ 30d,  τ_launch ≈ 120d
```

**6. Relationship Score (RS)** — graph strength of person↔company (or company↔need).
```
RS = f( edge_confidence, #independent_evidence_edges, edge_recency, path_specificity )
```

**7. Timeline Score (TS)** — does the *sequence* tell a coherent buying story?
```
TS = coherence(ordered_signals) · momentum(rate_of_recent_signals)
   coherence  = pattern match vs. known buying sequences (funding→hiring→pain)
   momentum   = normalized count of signals in the last window
```

**8. Opportunity Score (OS)** — the composite ranking number, tier-anchored.
```
OS = ( w1·BI + w2·ES + w3·FR + w4·RS + w5·TS + w6·CC + w7·IC ) · tier_multiplier(tier)
     tier_multiplier: Gold 1.0, Silver 0.7, Bronze 0.4
```
Tier anchors the band, but a strong Bronze can still out-rank a weak Silver on raw signal — intentional (O3). Every `score.components` row stores each sub-score and its inputs so the UI renders the full breakdown.

### 6.2 Decay & recomputation triggers
Scores are time-dependent (O6):
- **Event-driven recompute** — on any new signal/evidence/entity change for the company (hot path; keeps freshness SLA < 60 min, NFR-7).
- **Nightly decay sweep** — `scoring` + `decay` workers recompute FR/BI/OS (and `signal.decayed_score`) for all active opportunities, since freshness changes with the mere passage of time.
- **Config-change rescore** — editing the active `scoring_config` enqueues a background rescore of affected opportunities (O5), no redeploy.

Each recompute writes latest to `score` and appends to `score_history` (trend charts).

## 7. Processing Flow & Interfaces

```
signals.candidate ─┐
entity.upserted   ─┼─► [opportunity worker]
                   │      OpportunityEngine.evaluate(company_id)
                   │        → templates match → upsert opportunity → classify tier → transitions
                   │      ScoringEngine.score(opportunity)         → score vector → score/score_history
                   └─►  emit opportunity.changed ─► indexer (OpenSearch) + digest
```

```python
class OpportunityEngine:
    def evaluate(self, company_entity_id: int) -> list[OpportunityResult]:
        signals = repo.signals_for(company_entity_id)
        graph   = repo.neighborhood(company_entity_id)
        results = []
        for tmpl in TEMPLATES:
            if tmpl.matches(signals, graph):
                opp = self.upsert_opportunity(company_entity_id, tmpl, signals, graph)
                new_tier = classify(opp)
                if new_tier != opp.tier:
                    self.record_transition(opp, opp.tier, new_tier)
                    opp.tier = new_tier
                results.append(opp)
        return results

class ScoringEngine:
    def score(self, opp) -> ScoreVector:
        cfg = config.active_weights()
        v = ScoreVector(IC=..., CC=..., BI=..., ES=..., FR=..., RS=..., TS=...)
        v.OS = cfg.combine(v) * tier_multiplier(opp.tier)
        repo.upsert_score(opp, v); repo.append_history(opp, v)
        return v
```

## 9. Learning to Rank (later)

Once the operator marks Gold leads good/bad (feedback captured in the UI):
- Train a ranker (LambdaMART/GBM) on the **same feature vector** to produce OS.
- Keep the hand-tuned formula as **fallback and explainability baseline** (never lose explainability).
- Same loop learns the decision-maker inference mapping (§5.1) from converted Gold outcomes.

## 10. Quality, Metrics & Guards (hooks into doc 09)

| Metric | Definition | Purpose |
|---|---|---|
| **Precision@Gold** | operator-rated correctness of Gold | guards confident-but-wrong (blueprint R5) |
| **Promotion rate** | Bronze→Silver→Gold transitions / month | proves the flywheel |
| **Score monotonicity** | adding a stronger fresh signal must not lower BI/OS | invariant test in CI |
| **Explainability completeness** | 100% of scores have a `components` breakdown | invariant test |
| **False-intent rate** | sampled bad Gold / total Gold | tune intent weights |
| **Freshness distribution** | median signal age on surfaced opps | intent decays fast |

**Anti-false-positive design:** BI uses noisy-OR requiring independent corroboration; ES rewards source diversity; templates require `min_signals`; Gold requires *relationship* evidence — layered defenses against a single noisy signal producing a confident opportunity (R5).
